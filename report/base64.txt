2.8. Полный цикл: Unicode → UTF-8 → Base64 → байты → Unicode
==============================================================================
Text:          大学
UTF-8 bytes:   E5 A4 A7 E5 AD A6 (6 байт)

Decoded bytes: E5 A4 A7 E5 AD A6

Совпадение:    True

Цепочка:
Unicode text → UTF-8 bytes → Base64 ASCII text → bytes → UTF-8 decode → Unicode text

==============================================================================
Padding '=' на длинах, не кратных трём
==============================================================================
b'A'     (1 байт) -> QQ==     padding=2
b'AB'    (2 байт) -> QUI=     padding=1
b'ABC'   (3 байт) -> QUJD     padding=0
b'ABCD'  (4 байт) -> QUJDRA== padding=2
b'ABCDE' (5 байт) -> QUJDREU= padding=1

1 входной байт → 2 символа + '=='; 2 байта → 3 символа + '=';
3 байта → ровно 4 символа без padding.

==============================================================================
Обычный Base64 и URL-safe Base64
==============================================================================
raw bytes:        FB FF EF 01 02
base64:           +//vAQI=
urlsafe_b64encode:-__vAQI=
URL-safe replace: '+' -> '-', '/' -> '_'; '=' может сохраняться
decode standard:  FB FF EF 01 02
decode url-safe:  FB FF EF 01 02

Проверка полного круга на маленьком бинарном файле
==============================================================================
исходный файл:     source.bin, 271 байт
Base64-файл:       source.bin.b64, 365 байт
восстановленный:   restored.bin, 271 байт
SHA-256 исходный:  e6ca506bf8f0aeed3946e19d38ee1360156d2a1e2c8e725200e327144b72813a
SHA-256 восстановл.: e6ca506bf8f0aeed3946e19d38ee1360156d2a1e2c8e725200e327144b72813a
файлы совпадают:   True

Почему Base64 удобен в JSON/API: JSON-строка должна быть
текстом, а Base64 использует только ASCII-символы и не ломается
при передаче через текстовые каналы. Это не значит, что бинарные
данные всегда нужно хранить в БД как текст: бинарный тип СУБД
обычно компактнее и не требует лишнего кодирования/декодирования.
